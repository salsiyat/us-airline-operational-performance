1. Executive Summary¶

This Exploratory Data Analysis (EDA) examines 19.8 million flight records from U.S. airlines spanning 2023-2025, sourced from the Bureau of Transportation Statistics (BTS). Our analysis focuses on:

  • Operational Performance: Flight delays, cancellations, and on-time performance
  • Airport Efficiency: Traffic patterns and congestion at 361 commercial airports
  • Airline Comparison: Performance benchmarking across major U.S. carriers
  • Business Impact: Financial implications of operational disruptions

Key Statistics:¶

  • Total Flights Analyzed: 19,775,745
  • Time Period: January 2023 - October 2025
  • Airports: 361 commercial airports
  • Airlines: 15 major U.S. carriers
  • Geographic Coverage: All U.S. states and territories

2. Purpose and Objectives¶

2.1 Project Purpose¶

This EDA serves as the foundation for a comprehensive database systems project that will demonstrate:

Secondary Objectives:

# On-time performance
df_ontime = pd.read_sql("""
    SELECT 
        OP_UNIQUE_CARRIER as airline,
        COUNT(*) as total_flights,
        SUM(CASE WHEN CAST(ARR_DELAY AS DECIMAL(10,2)) <= 15 OR ARR_DELAY IS NULL 
            THEN 1 ELSE 0 END) as ontime_flights,
        ROUND(SUM(CASE WHEN CAST(ARR_DELAY AS DECIMAL(10,2)) <= 15 OR ARR_DELAY IS NULL 
            THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 2) as ontime_pct
    FROM stg_ontime
    GROUP BY OP_UNIQUE_CARRIER
    HAVING COUNT(*) > 100000
    ORDER BY ontime_pct DESC

# Overall delay statistics
df_delay_stats = pd.read_sql("""
    SELECT 
        COUNT(*) as total_flights,
        SUM(CASE WHEN CAST(CANCELLED AS UNSIGNED) = 1 THEN 1 ELSE 0 END) as cancelled,
        SUM(CASE WHEN CAST(DIVERTED AS UNSIGNED) = 1 THEN 1 ELSE 0 END) as diverted,
        SUM(CASE WHEN CAST(ARR_DELAY AS DECIMAL(10,2)) > 15 THEN 1 ELSE 0 END) as delayed_15min,
        AVG(CAST(DEP_DELAY AS DECIMAL(10,2))) as avg_dep_delay,
        AVG(CAST(ARR_DELAY AS DECIMAL(10,2))) as avg_arr_delay
    FROM stg_ontime
    WHERE DEP_DELAY IS NOT NULL
    LIMIT 1000000
""", engine)

# Calculate rates

# Delay causes analysis
df_causes = pd.read_sql("""
    SELECT 
        SUM(CAST(CARRIER_DELAY AS DECIMAL(15,2))) as carrier,
        SUM(CAST(WEATHER_DELAY AS DECIMAL(15,2))) as weather,
        SUM(CAST(NAS_DELAY AS DECIMAL(15,2))) as nas,
        SUM(CAST(SECURITY_DELAY AS DECIMAL(15,2))) as security,
        SUM(CAST(LATE_AIRCRAFT_DELAY AS DECIMAL(15,2))) as late_aircraft
    FROM stg_ontime
    WHERE CAST(ARR_DELAY AS DECIMAL(10,2)) > 15
    LIMIT 500000
""", engine)

# Create summary
causes_dict = {
    'Carrier Delay': df_causes['carrier'][0],
    'Weather Delay': df_causes['weather'][0],
    'NAS Delay': df_causes['nas'][0],
    'Security Delay': df_causes['security'][0],

df_causes_summary = df_causes_summary.sort_values('Total Minutes', ascending=False)

11. Next Steps: Database Design¶

11.1 Proposed Data Models¶

Based on our EDA, we will implement three database schemas:

1. Third Normal Form (3NF) - OLTP Database¶

Purpose: Transactional database with no redundancy

Proposed Tables:

  • airlines (dimension)
  • airports (dimension)
  • aircraft (dimension)
  • routes (dimension)
  • flights (fact)
  • flight_delays (fact - normalized separate table)
  • cancellation_reasons (reference)
  • delay_causes (reference)

3NF Requirements Met:

  • ✅ First Normal Form: Atomic values, unique rows
  • ✅ Second Normal Form: No partial dependencies
  • ✅ Third Normal Form: No transitive dependencies

Example:

flights table:
- flight_id (PK)
- airline_id (FK → airlines)
- origin_airport_id (FK → airports)
- dest_airport_id (FK → airports)
- route_id (FK → routes)
- flight_date
- scheduled_dep_time
- actual_dep_time
- etc.

flight_delays table (separate for 3NF):
- delay_id (PK)
- flight_id (FK → flights)
- carrier_delay_minutes
- weather_delay_minutes
- etc.

2. Star Schema - Data Warehouse¶

Purpose: Optimized for analytical queries

Dimensions:

  • dim_date (date hierarchy: day → month → quarter → year)
  • dim_airline (carrier information)
  • dim_airport (airport details + city + state + region)
  • dim_route (origin-destination pairs)
  • dim_delay_cause (delay categorization)

Facts:

  • fact_flight_performance (denormalized for speed)
    • All delay causes in same table
    • Calculated metrics included
    • Foreign keys to all dimensions

Star Schema Characteristics:

  • ✅ Single fact table surrounded by dimension tables
  • ✅ Denormalized dimensions (no snowflaking)
  • ✅ Optimized for SELECT queries
  • ✅ Simple JOIN paths

3. Snowflake Schema - Normalized Dimensions¶

Purpose: Reduce dimension table redundancy

Normalized Dimensions:

  • dim_airport → dim_city → dim_state → dim_region
  • dim_airline → dim_airline_type
  • dim_date → dim_month → dim_quarter → dim_year

Snowflake vs. Star:

  • ✅ Less storage (no repeated city/state names)
  • ✅ More normalized (closer to 3NF)
  • ⚠️ More complex queries (additional JOINs)
  • ⚠️ Potentially slower performance

11.2 Gap Analysis¶

Identified Gaps:

Gap Impact Solution
Missing tail numbers Cannot track aircraft Use airline + flight number as fallback
NULL delay causes Calculation complexity Create flag for on-time flights
Inconsistent date formats ETL complexity Standardize to DATE type
Geographic hierarchy Snowflake design Extract city/state/region tables

11.3 STTM (Source-to-Target Mapping)¶

Example Mappings:

Source: stg_ontime.ORIGIN_AIRPORT_ID
Target: flights.origin_airport_id (3NF)
Target: fact_flight_performance.origin_airport_key (Star)
Transformation: Direct mapping, validate FK exists
Data Type: INT

Source: stg_ontime.ARR_DELAY (VARCHAR)
Target: flights.arr_delay (3NF)
Target: fact_flight_performance.arr_delay_minutes (Star)
Transformation: CAST(ARR_DELAY AS INTEGER), handle NULL as 0
Data Type: INTEGER

Source: stg_ontime.ORIGIN_CITY_NAME
Target: airports.city (3NF)
Target: dim_airport.city (Star)
Target: dim_city.city_name (Snowflake)
Transformation: TRIM(), validate not NULL
Data Type: VARCHAR(100)

11.4 Design Methodology¶

Approach: Hybrid (Kimball + Inmon)

Phase 1: Staging (Current)

  • ✅ Raw data landing zone
  • ✅ No transformations
  • ✅ All source data preserved

Phase 2: OLTP (3NF)

  • Build normalized operational database
  • Support transactional queries
  • Enforce referential integrity

Phase 3: Data Warehouse (Star)

  • Create dimensional model
  • Optimize for analytics
  • Pre-calculate common metrics

Phase 4: Analytical Layer (Snowflake)

  • Normalize dimensions for storage efficiency
  • Support hierarchical queries
  • Enable drill-down analysis

ETL Process:

Staging → 3NF → Star Schema → Snowflake Schema
  ↓        ↓         ↓              ↓
Extract  Transform  Denormalize   Normalize
Load     Validate   Aggregate     Dimensions
